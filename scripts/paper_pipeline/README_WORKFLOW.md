# 工作流与当前边界

1. 使用具备目标 Obsidian 结构和本地原文的库，建立可校验的输入清单和 PDF 解析缓存。
2. 本地抽取文本候选并构建向量索引，保留来源位置和模型版本。
3. 审核方法、问题、任务、数据集以及对应关系；相似度和词段本身不是事实关系。
4. 在满足内容、幂等与可视化验收条件后，再由维护者决定是否发布到正式图谱。

现有冻结样本、数据库和人工审核附加档案不包含在本仓库。`card_enrichment.py` 的既有路径会读取人工审核附加档案，不能把该输出当作无人干预的自动成卡结果。当前100篇自动成卡验收未通过；有关输入结构和入口可通过模块的 `--help` 查看。

## 实验性候选和独立复核

`automatic_roles.py` 只从原句与模型证据生成未审核的角色候选；缺少可信证据、存在冲突或是否定语句时保留为 `unresolved`。`cold_pilot.py` 从原始 PDF 提取初始窗口，`fulltext_pilot.py` 扩展带线索的正文窗口，`metadata_author_candidates.py` 对照 PDF 元数据与首页文本，`audit_automatic_pilot.py` 生成来源复核包。它们依赖原项目的固定清单和缓存布局，仓库本身不包含可直接运行的那 100 篇输入。

`role_verifier.py` 可对复核包中的候选调用本地 Qwen3-1.7B，结果分为支持、不支持和不确定。输出是第二个未经验证的模型判断，并非事实审核；测试发现它仍会把部分错误候选判作支持。工具不更新正式图谱，不因候选数量多就制造关系，模型出错也不会标记论文缺失。

复跑可以复用按来源、模型和代码指纹校验的缓存；冷启动、缓存复跑、人工复核和完整端到端时间需要分别记录。对照样本应在查看模型输出前冻结；原句包含实体不代表语义正确，未审核候选不应自动升级为事实。
